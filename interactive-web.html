Worst Volume Interface

An intentionally frustrating interface that explores how breaking familiar UX conventions changes the user experience.

This project challenged me to design the worst possible way to change volume while keeping the interaction technically functional, playful, and possible to complete.

01

Context

Turning bad UX into a design experiment.

The assignment asked me to create the most frustrating, unintuitive, and deliberately poor interface possible for changing volume.

A traditional volume control is designed to be predictable, efficient, and immediately understandable. I approached this project by intentionally reversing those expectations. Instead of using a familiar slider, I created a button that moves away from the user as they approach it.

The challenge was not simply to make the interface unusable. It still needed to work, communicate its current volume, and provide a clear ending. The frustration needed to feel intentional and humorous rather than like an unfinished or broken website.

02

Ideation

Making a simple task unnecessarily difficult.

I explored ways to create friction by removing predictability, consistency, and user control.

01

Escaping control

The volume button moves when the cursor approaches, forcing the user to chase it around the screen.

02

Unexpected behavior

Every fourth successful click decreases the volume instead of increasing it.

03

False completion

The first attempt to submit the selected volume is rejected, requiring the user to confirm it again.

These ideas challenge familiar usability principles while still giving the user enough feedback to understand that the strange behavior is part of the experience.

03

Development

Combining movement, feedback, and conditional behavior.

The interaction was built with HTML, CSS, and JavaScript and published through GitHub Pages.

HTML

Interaction structure

HTML provides the volume display, moving button, meter, submission control, status messages, and final result screen.

CSS

Visual feedback

CSS transitions create smoother button movement and prevent the interface from appearing unintentionally glitchy.

JavaScript

Unpredictable behavior

JavaScript controls cursor proximity, randomized movement, volume changes, escape attempts, status messages, and the completion state.

04

Validation

Frustrating, but no longer accidentally broken.

Instructor feedback revealed that the initial version felt too glitchy and that clicks did not always register.

“Would love to see this not be janky when it moves. Triple check that the click interaction is working. Something to submit the volume once the interaction is complete.”

Instructor feedback

I revised the movement so the button escapes only some of the time, rather than every time the cursor comes near it. I also paused movement once the user pressed the button so the click could register correctly.

I added smooth CSS transitions, a visible escape counter, changing feedback messages, and a final submission flow. These revisions preserved the intentionally bad UX while making the project feel complete and deliberately designed.

05

Outcome

A playful demonstration of why usability matters.

The final interface actively works against the user while remaining functional and possible to complete.

This project showed me that even intentionally bad design requires careful decision-making. If the interaction is completely impossible, the user simply stops participating. The strongest version created tension and surprise without removing the possibility of success.

Designing against standard UX principles strengthened my understanding of consistency, feedback, predictability, user control, and trust. It also helped me practice using front-end development as a tool for interaction design and experimentation.
